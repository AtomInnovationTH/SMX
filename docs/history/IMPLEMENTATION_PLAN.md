### 1.1 `checkCollisions()` never called in `index.html`

| Attribute | Detail |
|-----------|--------|
| **Severity** | Critical — upgrades are 100% broken |
| **Complexity** | Trivial |
| **File** | [`index.html`](index.html:1690) |

**How to fix:**

Add `this.checkCollisions();` between [`updatePosition()`](index.html:1690) and [`spawnSpeedLines()`](index.html:1691):

```javascript
// index.html, inside update(), after line 1690
this.physics.updatePosition(this.monkey, dt, this.canvas.width, this.wave.x);
this.checkCollisions();  // ← ADD THIS LINE
this.particleSystem.spawnSpeedLines(this.monkey);
```

**Why this approach:** This mirrors exactly what [`Space_Monkey_Elevator.html`](Space_Monkey_Elevator.html:1793) does. Collision check must happen after position update but before rendering. No alternative needed — it's a missing line.

**Note:** Once consolidation (item 17) is complete, this bug disappears since both files share one source.

### 1.2 Grip slider is inverted in `Space_Monkey_Elevator.html`

| Attribute | Detail |
|-----------|--------|
| **Severity** | Critical — slider UX is backwards |
| **Complexity** | Trivial |
| **File** | [`Space_Monkey_Elevator.html`](Space_Monkey_Elevator.html:1720) |

**What's wrong:** At [line 1720](Space_Monkey_Elevator.html:1720):

```javascript
this.eventBus.on('settings:grip', (data) => { this.gripMultiplier = (101 - data.value) / 20; });
```

The formula `(101 - data.value) / 20` is inverted:
- Slider at **1%** → `(101 - 1) / 20` = **5.0** (strongest grip)
- Slider at **100%** → `(101 - 100) / 20` = **0.05** (weakest grip)

Compare with [`index.html`](index.html:1634) which has the correct formula:

```javascript
this.eventBus.on('settings:grip', (data) => { this.gripMultiplier = data.value / 20; });
```

**How to fix:**

```javascript
// Space_Monkey_Elevator.html line 1720 — remove the inversion
this.eventBus.on('settings:grip', (data) => { this.gripMultiplier = data.value / 20; });
```

This gives:
- Slider at **1%** → `1 / 20` = **0.05** (weakest)
- Slider at **100%** → `100 / 20` = **5.0** (strongest)

**Why this approach:** Matches [`index.html`](index.html:1634) which has the correct behavior. The grip slider range `[1, 100]` with divisor 20 maps to `[0.05, 5.0]`, a reasonable multiplier range.

**Alternatives considered:** Could remap to `[0.1, 1.0]` for a tighter range, but `data.value / 20` is what the working version uses and players can fine-tune via the slider.

### 1.3 Material dropdown and Tension slider do nothing

| Attribute | Detail |
|-----------|--------|
| **Severity** | Critical — two settings controls are non-functional |
| **Complexity** | Medium |
| **File** | [`Space_Monkey_Elevator.html`](Space_Monkey_Elevator.html:1301) (material), [line 1719](Space_Monkey_Elevator.html:1719) (tension) |

**What's wrong:**

1. **Material dropdown** ([line 1301–1308](Space_Monkey_Elevator.html:1301)): The `change` handler only updates the label text. It emits no event and changes no game state.

2. **Tension slider** ([line 1719](Space_Monkey_Elevator.html:1719)): `this.vineTension = data.value` stores the value, but [`vineTension`](Space_Monkey_Elevator.html:1436) is never read by physics — it's not used in [`calculateGrabMomentum()`](Space_Monkey_Elevator.html:1175), [`applyGravityAndDrag()`](Space_Monkey_Elevator.html:1202), or any other method.

**How to fix — Tension:**

Tension should affect the tether multiplier (how much momentum a grab transfers). Higher tension = more efficient energy transfer = higher momentum multiplier.

In [`setupEventListeners()`](Space_Monkey_Elevator.html:1709), update the tension handler:

```javascript
this.eventBus.on('settings:tension', (data) => {
    this.vineTension = data.value;
    // Tension affects momentum transfer: baseline 100kg -> 3.6x multiplier
    // Scale logarithmically from ~1.8x (1kg) to ~7.2x (20000kg)
    this.tetherMultiplier = GameConfig.PHYSICS.MOMENTUM_MULTIPLIER * 
        (0.5 + 0.5 * Math.log10(data.value) / Math.log10(20000));
});
```

**How to fix — Material:**

Material should emit a settings event and affect vine stiffness (which modulates wave propagation). In [`setupUIHandlers()`](Space_Monkey_Elevator.html:1290) within [`InputManager`](Space_Monkey_Elevator.html:1268):

```javascript
materialElement.addEventListener('change', (e) => {
    const selectedText = e.target.options[e.target.selectedIndex].text;
    document.getElementById('materialValue').textContent = selectedText;
    this.eventBus.emit('settings:material', { value: parseInt(e.target.value) });
});
```

In [`setupEventListeners()`](Space_Monkey_Elevator.html:1709) in [`SpaceMonkeyGame`](Space_Monkey_Elevator.html:1393):

```javascript
this.eventBus.on('settings:material', (data) => {
    // Material GPa affects wave amplitude damping
    // Higher GPa = stiffer tether = less amplitude attenuation
    // 50 GPa -> 0.7x amplitude, 300 GPa -> 1.0x amplitude
    const stiffnessRatio = data.value / 300;
    this.materialDamping = 0.7 + 0.3 * stiffnessRatio;
});
```

Then apply `this.materialDamping` in [`attemptGrab()`](Space_Monkey_Elevator.html:1762):

```javascript
attemptGrab() {
    const g = this.physics.calculateGrabMomentum(
        this.waveSystem, this.monkey,
        this.gripMultiplier * this.materialDamping,  // ← factor in material
        this.tetherMultiplier
    );
    // ... rest unchanged
}
```

Initialize `this.materialDamping = 1.0` in [`constructor()`](Space_Monkey_Elevator.html:1394) and [`initGame()`](Space_Monkey_Elevator.html:1643).

**Why this approach:** Both controls already have full UI (slider/dropdown), HTML elements, and event plumbing. The missing piece is only the physics integration. Logarithmic scaling for tension prevents the high end (20,000 kg) from dominating. Material stiffness as an amplitude damping factor is physically motivated — stiffer materials transmit vibrations more efficiently.

**Alternatives considered:**
- Making tension directly multiply momentum linearly — rejected because the 1–20,000 range would make low values useless.
- Making material purely cosmetic — rejected because players expect settings to affect gameplay.

```javascript
class LoadingManager {
    constructor() {
        this.totalAssets = 0;
        this.loadedAssets = 0;
        this.bar = document.getElementById('loadingBar');
        this.text = document.getElementById('loadingText');
    }
    
    register(count) { this.totalAssets += count; }
    
    assetLoaded(name) {
        this.loadedAssets++;
        const pct = Math.floor((this.loadedAssets / this.totalAssets) * 100);
        if (this.bar) this.bar.style.width = pct + '%';
        if (this.text) this.text.textContent = name || `Loading... ${pct}%`;
    }
    
    onComplete(callback) {
        this._checkInterval = setInterval(() => {
            if (this.loadedAssets >= this.totalAssets) {
                clearInterval(this._checkInterval);
                callback();
            }
        }, 100);
    }
    
    dismiss() {
        const screen = document.getElementById('loading-screen');
        if (screen) {
            screen.classList.add('fade-out');
            setTimeout(() => screen.remove(), 600);
        }
    }
}
```

**How to fix:**

Replace the restart handler with a two-step confirmation:

```javascript
// In setupEventListeners()
this.eventBus.on('input:restart', () => {
    if (this.monkey.altitude < 10) {
        // Near ground — no progress to lose, restart immediately
        this.initGame();
        return;
    }
    if (this._restartPending) {
        // Second R press within 2s — confirm restart
        clearTimeout(this._restartTimeout);
        this._restartPending = false;
        this.initGame();
    } else {

});
```

### 3.12 Hoist Parallax Math Out of Landmark Loop

| Attribute | Detail |
|-----------|--------|
| **Complexity** | Low |
| **File** | [`LandmarkSystem.update()`](Space_Monkey_Elevator.html:858) |

**What's wrong:** Inside the `forEach` at [line 859](Space_Monkey_Elevator.html:859), these values are recomputed for every landmark (70+) despite being identical across iterations:

- [`speed`](Space_Monkey_Elevator.html:875) = `Math.abs(monkeySpeed)`
- [`speedFactor`](Space_Monkey_Elevator.html:877) = `Math.min(speed / speedThreshold, 1.8)`

- [`maxParallax`](Space_Monkey_Elevator.html:885)
- [`maxAltitude`](Space_Monkey_Elevator.html:872) (constant `100000`)

**How to fix:**

Hoist loop-invariant calculations before the `forEach`:

```javascript
update(cameraAltitude, screenHeight, monkeySpeed = 0) {

    const maxAltitude = VISUAL_CONSTANTS.LANDMARK_MAX_ALTITUDE;
    const speed = Math.abs(monkeySpeed);
    const speedThreshold = VISUAL_CONSTANTS.LANDMARK_SPEED_THRESHOLD;
    const speedFactor = Math.min(speed / speedThreshold, 1.8);
    const baseMinParallax = VISUAL_CONSTANTS.LANDMARK_PARALLAX_MIN;
    const baseMaxParallax = VISUAL_CONSTANTS.LANDMARK_PARALLAX_MAX;
    const minParallax = baseMinParallax * (1 - speedFactor * 0.35);
    const maxParallax = baseMaxParallax;
    const parallaxRange = maxParallax - minParallax;
    
    this.landmarks.forEach(landmark => {
        const altDiff = Math.abs(landmark.altitude - cameraAltitude);
        if (altDiff > 15000) {
            if (landmark.element.style.display !== 'none') {
                landmark.element.style.display = 'none';
            }
            return;
        }
        
        const altitudeRatio = Math.min(landmark.altitude / maxAltitude, 1);
        const parallaxFactor = maxParallax - (altitudeRatio * parallaxRange);
        const parallaxDiff = (landmark.altitude - cameraAltitude) * parallaxFactor;
        const screenY = screenHeight / 2 - parallaxDiff * 10;
        
        // ... rest of rendering logic unchanged ...
    });
}
```

**Why this approach:** Pure computation hoisting — no behavioral change. Saves ~70 `Math.abs`, `Math.min`, and multiplication operations per frame. The `parallaxRange` pre-computation collapses one subtraction per iteration too.

### 3.14 Fix O(n) Pool Release

| Attribute | Detail |
|-----------|--------|
| **Complexity** | Low |
| **File** | [`ObjectPool.release()`](Space_Monkey_Elevator.html:1081) and [`ObjectPool.update()`](Space_Monkey_Elevator.html:1092) |

**What's wrong:** 

1. [`release()`](Space_Monkey_Elevator.html:1081) at line 1083 uses `this.active.splice(index, 1)` — O(n) array shift. [`index.html`](index.html:1043) has the O(1) swap-with-last pattern.

2. [`update()`](Space_Monkey_Elevator.html:1092) at line 1097 also uses `splice(i, 1)` inside the backward loop. This is less critical (already iterating backward) but still shifts elements.

**How to fix:**

```javascript
release(obj) {
    const index = this.active.indexOf(obj);
    if (index !== -1) {
        // O(1) swap-with-last removal
        const last = this.active.length - 1;
        if (index !== last) {
            this.active[index] = this.active[last];
        }
        this.active.pop();
        this.resetFn(obj);
        this.pool.push(obj);
    }
}

update(updateFn, dt) {
    for (let i = this.active.length - 1; i >= 0; i--) {
        const obj = this.active[i];
        const shouldRemove = updateFn(obj, dt);
        if (shouldRemove) {
            // O(1) swap-with-last removal (safe in backward loop)
            const last = this.active.length - 1;
            if (i !== last) {
                this.active[i] = this.active[last];
            }
            this.active.pop();
            this.resetFn(obj);
            this.pool.push(obj);
        }
    }
}
```

**Why this approach:** Swap-with-last is the standard O(1) unordered removal pattern. Particle/speed-line order doesn't matter for rendering. The backward loop in `update()` ensures the swapped element (from the end) gets processed on a subsequent iteration (since `i` decrements).

**Tradeoff:** Swap-with-last changes array ordering, which is fine for particles but would break ordered collections. Both pools (particles, speed lines) have no ordering requirement.

**Why this approach:** Static class property is allocated once. Lookup is O(1) property access instead of constructing a new object literal. The configs reference `COLOR_PALETTE` which is a const defined earlier, so static initialization order is safe.

**Tradeoff:** Object is shared (not copied per instance). Since `Upgrade` never mutates `this.config`, this is safe. If mutation were needed, use `Object.assign({}, Upgrade.CONFIGS[type])`.

```javascript
setupKeyboardHandlers() {

        this.keys[e.key] = true;
        if (e.key === ' ') this.eventBus.emit('input:grab', { pressed: true });

}
```

**Why this approach:** All input events flow through the `EventBus` consistently. Single `keydown` listener on `window`. No dead events. The pattern matches how grab, restart, and settings already work.
